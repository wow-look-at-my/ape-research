# macOS arm64 loader: hostile-Apple survivability — consolidated findings

Scope: Apple arm64 only. Linux and Windows loaders are untouched.

Two parallel investigations were run (Option A: content-based discovery;
Option B: minimal dependency surface), plus direct verification of the
load-bearing claims. Everything below was measured on macOS 26.5 / Apple M5
unless noted. Claims sourced from Apple's published code are cited by file,
relative to the research/dyld submodule (apple-oss-distributions/dyld, tag
dyld-1378).

---

## 1. The corrected premise

The prior session's transcript asserted two things that are false, and both
mattered:

1. **"macOS does not allow raw syscalls; SVC crashes with SIGSYS."** False.
   Raw `svc #0x80` works. Only syscall **class 0** (`x16` a small value) raises
   SIGSYS. Classes 1 (mach trap), 2 (BSD), 3, 4 all work, and an *invalid*
   syscall number inside a valid class returns an error code (0xe = EFAULT,
   0x26 = ENOSYS) rather than trapping. A bogus number is safe; a class-0 one
   is fatal.
2. **"The blocker is code signing / AMFI."** False. An *unsigned*
   dynamically-linked binary runs fine. The real constraint is a **linkage**
   rule (below), and its failure mode is not signing-related.

---

## 2. What actually blocks us, and where

Three separate enforcement points, each verified:

| # | dependency | enforced by | evidence |
|---|---|---|---|
| 1 | `LC_LOAD_DYLINKER` == exactly `/usr/lib/dyld` | XNU kernel | any deviation → SIGKILL (137) **before any user instruction runs** |
| 2 | dyld must find `/usr/lib/system/libdyld.dylib` | dyld, literal `strcmp` | `DyldRuntimeState.cpp:467` |
| 3 | dyld must find `/usr/lib/libSystem.B.dylib` | dyld, literal `strcmp` | `DyldRuntimeState.cpp:469` |
| 4 | ≥1 resolving dylib edge, **iff minos ≥ 15.4** | dyld `Policy::enforceHasLinkedDylibs()` | measured boundary exactly 15.3→15.4 |
| 5 | `filetype` must be `MH_EXECUTE` (2) | kernel | other filetypes → `Exec format error` (126) |
| 6 | `MH_DYLDLINK` flag must be set | kernel | clearing it → SIGKILL (137) |
| 7 | class-0 raw syscalls are fatal | kernel | SIGSYS (140) |

Apple's source, verbatim (`dyld/DyldRuntimeState.cpp:459-471`):

```c
if ( strlen(installName) > prefixLength ) {
    if ( (strcmp(installName + prefixLength, "/usr/lib/system/libdyld.dylib") == 0)
      || (strcmp(installName, "/usr/lib/system/libdyld.dylib") == 0) )
        setDyldLoader(ldr);
    else if ( (strcmp(installName + prefixLength, "/usr/lib/libSystem.dylib") == 0)
           || (strcmp(installName, "/usr/lib/libSystem.B.dylib") == 0) )
        libSystemLoader = ldr;
}
```

There is no content fallback, no UUID check, no inode check — a literal string
compare. `dyldMain` then halts unconditionally if either loader is null.

Sharpest consequence: **even a binary with zero dylib load commands does not
escape the name.** dyld *synthesizes* the libSystem edge as the literal string
(`mach_o/UnsafeHeader.cpp:1403-1422`).

## 3. The finding that changes the design: the minos-15.4 gate

`Policy::enforceHasLinkedDylibs()` is gated on the **binary's own** minos (the
spring-2025 enforcement epoch). Measured, rebuilding the same zero-dylib binary
at each minos:

```
minos 11.0 ... 15.3   runs   (rc=0)
minos 15.4 and later  abort  dyld: missing LC_LOAD_DYLIB (must link with at least libSystem.dylib)
```

Boundary is exactly **15.4**. A binary declaring `minos 11.0` with **zero dylib
load commands** launches. This is not a byte-patch or a signature trick: we
simply declare the oldest target, which is legitimate and also what backward
compatibility wants.

This is not hypothetical — the same gate broke real software in the field:
Wine (Sikarugir/WineCX), Valgrind-macos, and ChimeraX's pyKVFinder all report
byte-identical `missing LC_LOAD_DYLIB (must link with at least libSystem.dylib)`
aborts. That is precisely the hostile-upgrade behavior this work exists to
survive.

Caveat: minos is a floor, not a ceiling — the binary still runs on 26.5. But
*which* policy dyld applies to a given minos is dyld behavior Apple can change.

---

## 4. Cheapest high-value hardening: a second weak dylib reference

Measured, not theorised. With two weak references, one surviving any single
rename keeps the launch alive:

```
weak libSystem.B + weak libz.1:
  baseline                 rc=4
  libSystem.B renamed away rc=4   STILL RUNS

weak libSystem.B only:
  renamed away             abort  dyld: libdyld.dylib not found (134)
```

Cost: one load command (~48 bytes). Effect: converts a hard abort into a
successful launch under any single-library rename. This is redundancy, not
immunity — renaming *both* still aborts.

## 5. Can we survive Apple renaming libSystem? No — and it is disproven, not assumed

Content-based discovery (Option A) was built end to end and works: it resolves
**53/53 Syslib symbols with zero undefined symbols and zero dylib load
commands**, matching `dlsym` for 184/187 names, with pointers verified
*callable*. It never reads a path. Its robustness is real: 3646/3646 cache
images parse, 3,641,939 symbols, zero malformed.

But it **cannot** survive the stated rename scenario, because dyld halts at
`dyld_main → prepare() → state.add()` **before our loader is entered**
(dependency #3 above). So:

- **libSystem renamed, today's dyld** → dyld aborts first. Option A and Option B
  die identically; the cache parser is dead code.
- **A future dyld that stopped name-matching** → Option A survives; a
  weak-linking loader on minos ≥ 15.4 with no surviving edge aborts.

Content discovery only pays off in the world where Apple *also* fixes dyld's own
brittleness — i.e. the world where the attack is already defanged.

**Do not brief this as "survives a libSystem rename."** It is false in the exact
scenario that matters.

## 6. Where content discovery genuinely wins

Two real, non-hypothetical payoffs:

1. **Immunity to cache reorganisation.** `libSystem.B.dylib` exports only 3
   symbols and re-exports 39 sub-libraries; all 53 Syslib entries actually live
   in sub-libraries. A loader hard-linking `libSystem.B` and trusting its flat
   namespace is the fragile one. Content discovery is indifferent to which image
   holds an export, and handles a symbol moving between images.
2. **It eliminates the loader's own `dlopen`/`dlsym` use.** `apeld.c` and
   `ape-m1.c` fill 4 of 53 Syslib slots via `dlopen`/`dlsym`, which live in
   `libdyld.dylib`. Sourcing the table from the cache removes the last runtime
   dependency on dyld's public API — the loader becomes a pure reader of mapped
   memory plus raw syscalls. Trade: raw pointers cannot be re-resolved after an
   OS update, which is acceptable for a short-lived loader.

## 7. Verified facts about the loader's core mechanic

With **zero imports** and raw syscalls only:

- `mmap` RW anon → write code → `mprotect` RX → **jump works** (executed mapped
  code, returned 42).
- **RWX is refused** (`EACCES`). W^X is enforced; text must be RW → fill →
  `mprotect` RX.
- **`MAP_FIXED` at `0x40000000000`** (the cosmo arm64 link base) succeeds
  *exactly*. Note `0x100000000` fails with `ENOMEM` because the loader itself is
  mapped there.
- `LC_MAIN` yields correct `argc`/`argv`/`envp` with zero imports.
  `LC_UNIXTHREAD` does **not** produce a proper argc/argv stack block.
- The 4th argument to `main` (`x3`) is dyld **launch parameters** as
  `key=value` strings (`executable_path=`, `executable_cdhash=`, ...), read via
  `_simple_getenv` (`DyldProcessConfig.cpp:572`) — **not** a libSystem pointer
  table. `executable_path=` is a usable source for `AT_EXECFN`.

### Authoritative shared-cache layout

From Apple's published `include/mach-o/dyld_cache_format.h`
(apple-oss-distributions/dyld), offsets computed by summing the struct:

| field | offset |
|---|---|
| `mappingOffset` / `mappingCount` | `0x10` / `0x14` |
| `imagesOffsetOld` / `imagesCountOld` | `0x18` / `0x1C` — **retired, zero** |
| `sharedRegionStart` / `sharedRegionSize` | `0xE0` / `0xE8` |
| **`imagesOffset`** | **`0x1C0`** |
| **`imagesCount`** | **`0x1C4`** |
| total header size | `0x228` (552) |

Verified against the live cache: `imagesOffset=664`, `imagesCount=3646`, and
`sharedRegionStart=0x180000000` matching the process slide. The earlier
guesses (`0x18`, `0xE0`) are exactly why the first parser attempts segfaulted.

`dyld_cache_image_info` is 32 bytes: `addr(8) modTime(8) inode(8)
pathFileOffset(4) pad(4)`, where `addr` is **unslid** and the path is at
`cacheBase + pathFileOffset`.

Symbol resolution via `LC_SYMTAB` (chosen over the export trie for simplicity):
names carry a leading underscore (`_getpid`); accept only `N_SECT` symbols (an
unfiltered walk returns undefined entries whose `n_value` is 0).

## 9. Corrections from Option B (verified independently)

Option B found three errors in the ground truth I had handed both agents, and I
reproduced all three. Two of them were bugs in my own running code.

| my earlier claim | measured reality |
|---|---|
| raw `pipe(42)` writes `fd[0]` and `fd[1]` | **false.** It returns one fd in `x0` and leaves the caller's array untouched. Two calls make two *unrelated* pipes — a write to one never appears on the other. `pipe` must come from libSystem. |
| mach traps are `0x1000000 &#124; n` | **false.** They use **negative** `x16`. `-28` returns 515 (`mach_task_self`); `0x1000000&#124;28` returns 14. |
| any invalid syscall number returns an error | **too broad.** BSD 101 (`nanosleep`) is **SIGSYS-fatal**. Invalid numbers in valid *classes* return errors; this one traps. |

Also confirmed: mach traps do **not** use the carry/negate errno convention —
they return in `x0` directly.

And one behavioural trap worth recording: raw `fork` returns the **child's pid in
the child**, not 0, and raw `sigaction` installs but **never delivers** a
handler. Both would silently corrupt a payload relying on them, which is why
those two are sourced from the cache rather than reimplemented.

Option B's structural finding also holds: `LC_LOAD_WEAK_DYLIB` makes a *symbol*
optional, not the *library set*. Two absent weak dylibs still abort. A
`@loader_path`-relative hedge library we control (8 bytes) is the only thing that
converts dyld's hard abort into a launch when libSystem is renamed — and even
that does not survive dyld's own literal-name check.

**Reimplementing pthread primitives on `__psynch_*`/`__semwait_signal` is
flagged reckless by both investigations.** Those are private kernel contracts
under real C functions. The runtime independently agrees: it parks Ms on
*`dlsym`'d* pthread primitives precisely because those objects must stay opaque.

## 10. The port: done, and verified locally

`/tmp/apex/apeld2.c` implements the design and boots a real arm64 APE.

Built with `-weak-lSystem`, `minos 11.0`, `LC_MAIN`, zero imports.

| property | before | after |
|---|---|---|
| undefined symbols | 67 | **0** |
| dylib load commands | 1 (strong) | 1 (weak; droppable at minos 11.0) |
| size | 36944 B | 33976 B |
| boot of a real arm64 APE | — | **works** |

Acceptance suite, 8/8, comparing against the stock shell boot as baseline:

```
PASS  args          args=["/tmp/apex/probe-arm64.com" "a" "b" "c"]
PASS  os.Executable exe="/tmp/apex/probe-arm64.com" exeErr=<nil>
PASS  env           env="yes"
PASS  platform      goos=darwin goarch=arm64 ncpu=10
PASS  exit status   3
PASS  missing file  127
PASS  no args       127
PASS  no payload    127
```

Key implementation details, each forced by measurement:

- **53 Syslib entries**, of which the syscall-shaped ones (`mmap`, `mprotect`,
  `pread`, `write`, `read`, `close`, `munmap`, `openat`, `getentropy`, `exit`,
  `clock_gettime`, `nanosleep`) are our own raw-syscall wrappers, and the rest
  (`pthread_*`, `dispatch_*`, `sysctl*`, `dlopen`/`dlsym`, `pipe`, `fork`,
  `sigaction`) are resolved **by content** from the shared cache.
- **`os.Executable()` needs an absolute `argv[0]`.** Cosmopolitan resolves it
  from `argv[0]` on hosts without procfs (`executable_cosmo.go:resolveArgv0`), so
  a bare relative name yields an empty result. The loader prefixes `$PWD`.
- **W^X**: segments map anonymous RW, fill, then `mprotect` to the final
  protection. `MAP_FIXED` at the payload's link address (`0x800000000` for this
  APE) succeeds exactly.
- **`environ` is not read**; the environment pointer comes from the third
  `LC_MAIN` argument. `strlen` is avoided with an explicit `no_builtin`
  attribute. Together these took the last 3 imports to 0.

### Still open

- Local results are from one machine (macOS 26.5, M5) inside a seatbelt sandbox.
  CI on the runner matrix is required before this is called done, including a
  real macOS 11 runtime (which no one here has) to prove the minos-11 claim on
  actual Big Sur.
- The port needs to land in the repo: `darwin/apeld.c`, `build.sh`, the CI
  static-linkage assertions, and the test expectations.
- The `pipe`/`fork`/`sigaction` entries depend on cache-resolution at runtime.
  If the cache is unavailable, those degrade to null and a payload that needs
  them fails. A fallback for that case is not implemented.


1. **Ship the minimal surface first**: zero imported symbols, raw syscalls for
   everything syscall-shaped, `LC_MAIN`, `-weak-lSystem`.
2. **Add a second weak dylib reference** (~48 bytes). Best ratio in this report.
3. **Set `minos 11.0`** so the spring-2025 gate stays grandfathered — and keep a
   weak edge anyway, so we are not relying on the grandfather clause alone.
4. **Then add content discovery as the Syslib source**, for cache-reorganisation
   immunity and to drop `dlopen`/`dlsym`.
5. **Do not claim rename immunity.** It is disproven.
6. **Keep the `shared_region_check_np` fallback** (scan up from `sp` for a
   16K-aligned pointer validating as a cache header) — ~20 lines, verified.

### Risk ledger

| claim | status |
|---|---|
| raw SVC works; only class 0 traps | proven |
| kernel requires literal `/usr/lib/dyld` | proven (any deviation → SIGKILL) |
| dyld requires literal libSystem/libdyld names | proven from Apple source |
| minos ≤ 15.3 with zero dylib cmds runs | proven, boundary measured at 15.4 |
| second weak ref rescues a single rename | proven |
| loader can mmap/mprotect/jump zero-import | proven |
| `MAP_FIXED` at 0x40000000000 exact | proven |
| cache offsets 0x1C0/0x1C4 | proven (3 independent ways) |
| 53/53 Syslib by content, zero imports | proven |
| **survives a libSystem rename** | **disproven** |
| zero-dylib escapes the name dependency | **disproven** (dyld synthesizes it) |
| behavior under a future cache format change | assumed — field validation only |
